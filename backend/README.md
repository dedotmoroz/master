# Naiti Mastera backend

Backend развивается как гексагональный модульный монолит. Бизнес-ядро не зависит от HTTP-фреймворка, PostgreSQL, почтового провайдера или облачного хранилища.

## Что реализовано

- `identity`: подтверждённые аккаунты и роли-возможности (`customer`, `contractor`, `admin`);
- `attachments`: асинхронно проверяемые загрузки профиля и гостевых заказов в S3-совместимое объектное хранилище;
- `contractors`: публичные профили исполнителей, специализации, география и портфолио;
- `catalog`: единый иерархический справочник категорий работ и карта старых ID;
- `geography`: российские регионы и населённые пункты с картой старых ID;
- `marketplace`: заявка гостя, подтверждение email, заказ и отклики;
- `reputation`: отзывы только по завершённым заказам;
- PostgreSQL-адаптеры для аккаунта, заявки, заказа, отклика, отзыва и сессии;
- транзакционная публикация заказа с блокировкой заявки `FOR UPDATE`;
- transactional outbox для доменных событий и отправки письма;
- уведомления в кабинете и по email о новых откликах, выборе исполнителя и завершении заказа;
- индивидуальные настройки email по каждому типу событий, включая письма в очереди;
- HTTP API на Fastify с проверкой тела запросов и единым форматом ошибок;
- Bearer-аутентификация по хешированным серверным сессиям;
- passwordless-регистрация и вход по одноразовой email-ссылке, выход из одной или всех сессий;
- смена email с подтверждением нового адреса, уведомлением старого и отзывом прежних сессий;
- удаление аккаунта по email-подтверждению с проверкой сделок, обезличиванием и очисткой файлов;
- кабинет заказчика: список, просмотр и отмена собственных заказов;
- редактирование условий и вложений собственного заказа до выбора исполнителя;
- публичная лента опубликованных заказов с фильтрами и пагинацией;
- полнотекстовый поиск заказов и исполнителей с географическими, бюджетными и рейтинговыми фильтрами;
- отклики исполнителей: подача, просмотр своих, отзыв и выбор победителя;
- завершение сделки участником и двусторонние отзывы после завершения;
- публичная карточка исполнителя с рейтингом, отзывами и числом завершённых заказов;
- публичное дерево категорий с проверкой активных выбираемых специализаций;
- создание и редактирование профиля исполнителя с портфолио;
- PostgreSQL rate limiting и Cloudflare Turnstile для публичной выдачи upload URL;
- фоновая очистка просроченных и не привязанных гостевых объектов;
- проверка файлов через ClamAV, безопасное перекодирование изображений без EXIF и генерация WebP-превью;
- SMTP-адаптер писем и локальный development-режим;
- liveness/readiness endpoints и корректное завершение процесса;
- SQL-схема для аккаунтов, заказов, откликов, отзывов, вложений, сессий и outbox;
- юнит- и PostgreSQL-интеграционные тесты.

Направление зависимостей:

```text
adapters -> application -> domain
```

## OpenAPI и Swagger

После запуска API (`npm start`) документация доступна на том же порту:

- Swagger UI: [http://localhost:3000/docs/](http://localhost:3000/docs/)
- OpenAPI JSON: [http://localhost:3000/openapi.json](http://localhost:3000/openapi.json), также `/docs/json`
- OpenAPI YAML: [http://localhost:3000/docs/yaml](http://localhost:3000/docs/yaml)

Swagger поддерживает **Try it out** и **Authorize**: вставьте только `session.token`, без слова `Bearer`. Токен не сохраняется после перезагрузки страницы. CSS/JS Swagger раздаются самим backend, внешний CDN и внешний валидатор не используются.

Спецификация OpenAPI 3.0.3 генерируется из зарегистрированных маршрутов и их реальных схем запросов. В контракте также описаны ответы, ошибки, заголовки `Retry-After` / `WWW-Authenticate`, Bearer security, ограничения и примеры запросов. Схемы ответов документации не меняют сериализацию бизнес-методов. Все существующие маршруты покрыты тестом полноты; успешные ответы и ошибки сверяются со схемами, включая сквозные PostgreSQL-сценарии.

Для передачи frontend сохранены [OpenAPI JSON](./docs/openapi.json) и [сценарии подключения](./docs/frontend-workflows.md). Обновление и проверка контракта не требуют PostgreSQL, S3, SMTP или `.env`:

```bash
npm run openapi:export
npm run test:openapi
```

Экспорт в другой файл: `npm run openapi:export -- /absolute/path/openapi.json`. При изменении маршрутов, схем запросов или моделей ответов обновите экспорт: тест сравнивает сохранённый JSON с документом работающего API.

## Гостевой заказ

1. Гость запрашивает загрузку файла и получает подписанный `PUT` URL вместе с секретным claim-токеном. В БД хранится только хеш claim-токена.
2. После прямой загрузки в S3 backend проверяет MIME и размер объекта через `HEAD` и переводит файл в `processing`.
3. Outbox-worker читает закрытый сырой объект с ограничением размера, проверяет его ClamAV, декодирует изображения через Sharp, удаляет метаданные и создаёт WebP-превью. Только после этого файл получает статус `ready`.
4. `SubmitGuestOrderHandler` сохраняет заявку и атомарно резервирует готовые файлы по парам `attachmentId + claimToken`.
5. Событие `GuestOrderSubmitted` попадает в outbox в той же транзакции. Сырой email-токен в БД не хранится.
6. Worker восстанавливает детерминированный HMAC-токен и передаёт его почтовому адаптеру.
7. `ConfirmGuestOrderHandler` блокирует заявку, находит или создаёт аккаунт, публикует заказ, передаёт ему гостевые вложения и подтверждает заявку в одной транзакции.
8. Повторный или одновременный переход по ссылке идемпотентен: создаётся один аккаунт и один заказ.

## Категории работ

```text
GET /api/v1/work-categories
```

Endpoint без авторизации возвращает дерево из трёх корневых разделов: строительство, ремонт и отделка, бытовые и строительные услуги. Корневые разделы служат только для группировки; в заказе и профиле исполнителя разрешены только активные категории с `selectable: true`.

Один и тот же справочник используется полем `categoryId` заказа и массивом `specializationIds` профиля. Специализации хранятся в нормализованной таблице many-to-many. Миграция содержит 50 очищенных категорий и 92 соответствия всем записям старых таблиц `sed_projects_cat` и `sed_freelancers_cat`, включая объединённые дубли.

## География России

```text
GET /api/v1/regions
GET /api/v1/locations?query=Моск&regionId=ru-region-43&limit=20
```

Страна фиксирована как Россия (`countryCode: RU`), поэтому отдельного справочника стран и выбора страны в API нет. Первый endpoint возвращает регионы, второй ищет населённые пункты по двум и более символам и при необходимости ограничивает поиск регионом. Если передан `regionId`, запрос можно выполнить без строки поиска.

Один справочник проверяет `locationId` заказа и `serviceLocationIds` профиля исполнителя. География профиля хранится в нормализованной many-to-many таблице. Начальная миграция переносит из старой базы 83 региона и 668 населённых пунктов, сохраняет 840 ссылок на старые ID и заменяет использовавшийся ранее временный ID `moscow-region`.

## Регистрация и вход

```text
POST   /api/v1/auth/registrations
POST   /api/v1/auth/registrations/confirm
POST   /api/v1/auth/login-requests
POST   /api/v1/auth/login-requests/confirm
POST   /api/v1/auth/email-change-requests
POST   /api/v1/auth/email-change-requests/confirm
GET    /api/v1/auth/me
DELETE /api/v1/auth/session
DELETE /api/v1/auth/sessions
```

Регистрация не создаёт аккаунт до подтверждения email. Первый endpoint всегда отвечает `202 pending_email`, а одноразовая ссылка действует 15 минут. Если подтверждённый email уже принадлежит активному аккаунту, регистрация безопасно превращается во вход без создания дубликата. Запрос входа для неизвестного или неактивного email возвращает такой же ответ, но письмо не отправляется.

В PostgreSQL сохраняется только SHA-256-хеш magic-link токена. После подтверждения токен помечается использованным в той же транзакции, где создаются аккаунт и сессия. Повторное использование ссылки запрещено. Частота запросов ограничивается независимо по IP и нормализованному email; исходные IP и email в таблице rate limit не хранятся, поскольку ключи защищены HMAC.

### Смена email

Авторизованный пользователь отправляет `POST /api/v1/auth/email-change-requests` с телом `{"email":"new@example.com"}`. Ответ — `202 {"status":"pending_email"}`. До подтверждения аккаунт сохраняет прежний адрес. Новый запрос аннулирует предыдущую ссылку этого аккаунта. Используется общий лимит email-запросов по IP и адресу.

Worker отправляет ссылку `/auth/email-change/confirm?token=...` на новый адрес. Frontend передаёт токен в `POST /api/v1/auth/email-change-requests/confirm` с телом `{"token":"..."}`; подтверждение не требует сессии и отвечает `204`. Ссылка одноразовая, по умолчанию действует 15 минут (`AUTH_LINK_TTL_SECONDS`). В БД сохраняется только хеш токена.

Занятость нормализованного email проверяется при запросе и при подтверждении; конфликт возвращает `409 EMAIL_ALREADY_IN_USE`. Совпадение с текущим адресом — `422 EMAIL_UNCHANGED`, неизвестный, отозванный или использованный токен — `404 INVALID_EMAIL_CHANGE_TOKEN`, истёкший — `410 EMAIL_CHANGE_EXPIRED`.

Подтверждение атомарно меняет email, помечает запрос использованным, отзывает все сессии и незавершённые ссылки регистрации/входа на прежний адрес. ID аккаунта, его роли, заказы и профиль сохраняются. После этого пользователь входит через новый email. На старый адрес через outbox отправляется уведомление о смене; сбой почты повторяется worker и не откатывает подтверждённую смену адреса. В development письма выводятся в лог.

### Удаление аккаунта

```text
POST /api/v1/auth/account-deletion-requests
POST /api/v1/auth/account-deletion-requests/confirm
```

Первый endpoint требует Bearer-сессию, берёт аккаунт из неё и отвечает `202 pending_email`. Ссылка приходит на текущий email и по умолчанию действует 15 минут (`AUTH_LINK_TTL_SECONDS`). Новый запрос аннулирует предыдущую ссылку. Подтверждение — публичный POST с телом `{"token":"..."}`; GET по ссылке сам по себе ничего не удаляет. Успешное подтверждение отвечает `204`, повторное — `404 INVALID_DELETION_TOKEN`, просроченное — `410 DELETION_TOKEN_EXPIRED`. В БД хранится только хеш токена.

На обоих этапах проверяется отсутствие заказов `in_progress`, где пользователь является заказчиком или выбранным исполнителем. Иначе возвращается `409 ACCOUNT_HAS_ONGOING_ORDERS`. Выбор исполнителя блокирует аккаунты участников, поэтому подтверждение удаления и назначение на работу не могут одновременно завершиться успешно. Смена email делает ранее выданную ссылку удаления недействительной.

При подтверждении аккаунт получает статус `deleted` и технический email на домене `accounts.invalid`; роли и профиль удаляются, сессии отзываются, ссылки входа, смены email и гостевой публикации аннулируются. Системные email и контактное имя в заявках обезличиваются. Публичные профиль, открытые заказы и выдача ссылок на файлы закрываются сразу. Это необратимая пользовательская операция: восстановления аккаунта через API нет.

Событие `AccountDeleted` запускает фоновую очистку: незавершённые опубликованные заказы отменяются, активные отклики закрываются, вложения удаляются из истории и хранилища. Worker ждёт истечения upload URL и повторяет неудачные удаления. Ранее выданные download URL ограничены своим сроком действия. Обработка изображений не восстанавливает файл, удалённый параллельной очисткой.

ID удалённого участника, завершённые сделки и отзывы сохраняются для истории. Произвольный текст заказов, откликов и отзывов автоматически не переписывается: удаление обезличивает системные поля аккаунта, а не ищет персональные сведения внутри пользовательского текста. Логи, почтовые ящики получателей и резервные копии управляются отдельно от рабочего API.

## Локальный запуск API

```bash
cp .env.example .env
docker compose up -d --wait postgres storage clamav
npm run storage:init
npm start
```

В `.env.example` включён `RUN_MIGRATIONS_ON_START=true`. Для production миграции лучше запускать отдельной командой перед развёртыванием:

```bash
npm run db:migrate
```

Создание гостевого заказа:

```bash
curl -X POST http://localhost:3000/api/v1/guest-orders \
  -H 'content-type: application/json' \
  -d '{
    "email": "customer@example.com",
    "contactName": "Анна",
    "categoryId": "house-building",
    "locationId": "ru-locality-1",
    "title": "Построить загородный дом",
    "description": "Ищу бригаду для строительства дома по готовому проекту.",
    "budgetMinMinor": 500000000,
    "budgetMaxMinor": 700000000,
    "temporaryAttachments": [
      {
        "attachmentId": "ATTACHMENT_ID",
        "claimToken": "ATTACHMENT_CLAIM_TOKEN"
      }
    ],
    "consentVersion": "2026-01"
  }'
```

В development-режиме worker выводит ссылку подтверждения в лог. Frontend получает из неё токен и отправляет:

```bash
curl -X POST http://localhost:3000/api/v1/guest-orders/confirm \
  -H 'content-type: application/json' \
  -d '{"token":"TOKEN_FROM_CONFIRMATION_LINK"}'
```

В ответе подтверждения приходит Bearer token. Защищённые endpoints:

```text
GET  /api/v1/customer/orders?limit=20&offset=0
GET  /api/v1/customer/orders/:orderId
PUT  /api/v1/customer/orders/:orderId
POST /api/v1/customer/orders/:orderId/cancel
```

Пример:

```bash
curl http://localhost:3000/api/v1/customer/orders \
  -H 'authorization: Bearer SESSION_TOKEN'
```

Сессии проверяются по хешу, сроку действия, отзыву и статусу аккаунта. Доступ к чужому заказу возвращает обычный `404`, не раскрывая его существование. Повторная отмена идемпотентна; отменять заказ после выбора исполнителя нельзя.

Редактирование заказа — `PUT /api/v1/customer/orders/:orderId` с полным набором редактируемых полей:

```json
{
  "categoryId": "foundation",
  "locationId": "ru-region-43",
  "title": "Фундамент нового дома",
  "description": "Нужно залить монолитный фундамент.",
  "budgetMinMinor": 100000000,
  "budgetMaxMinor": 200000000,
  "attachmentIds": []
}
```

Разрешены статусы `draft` и `published`; для `in_progress`, `completed`, `cancelled` возвращается `409 ORDER_NOT_EDITABLE`. Владелец определяется по сессии. Категория и локация проверяются по справочникам; бюджет задаётся в копейках или `null`. Статус, владелец и даты не редактируются, неизвестные поля запроса отклоняются. Дата публикации сохраняется, существующие отклики остаются. Повторное сохранение одинаковых данных не создаёт нового события `OrderUpdated`.

Для добавления файла авторизованный заказчик использует обычный endpoint загрузки с `purpose: "order"`, подтверждает загрузку и дожидается `ready`. Редактирование принимает до десяти уникальных `attachmentIds`, принадлежащих заказчику: новые файлы `order` и ранее переданные ему после подтверждения email файлы `guest_order`. Пустой массив убирает все вложения из заказа. Удалённый из заказа файл больше не получает публичные download URL, если он не используется в другом публичном объекте; уже выданные URL действуют до истечения своего срока.

Изменения выполняются в транзакции с `FOR UPDATE` на заказе, как и выбор исполнителя. Полнотекстовые и бюджетные индексы PostgreSQL обновляются при сохранении.

Публичная лента:

```text
GET /api/v1/orders?query=загородный дом&categoryId=house-building&regionId=ru-region-1&budgetMinMinor=100000&budgetMaxMinor=1000000000&sort=relevance&limit=20&offset=0
GET /api/v1/orders/:orderId
```

Доступные сортировки заказов: `newest`, `budget_asc`, `budget_desc`, `popular`, `relevance`. Без поисковой строки используется `newest`, с поисковой строкой — `relevance`. Фильтр региона находит как заказы, привязанные к самому региону, так и заказы в его населённых пунктах. Бюджетный фильтр проверяет пересечение диапазонов. Ответ сразу содержит `categoryName`, `locationName`, `regionId` и `regionName`.

Поиск исполнителей:

```text
GET /api/v1/contractors?query=строительство домов&specializationId=house-building&regionId=ru-region-43&minRating=4&sort=rating&limit=20&offset=0
GET /api/v1/contractors/:contractorId
```

Сортировки исполнителей: `rating`, `completed`, `newest`, `relevance`. В списке и публичном профиле вместе с массивами ID возвращаются объекты `specializations` и `serviceLocations` с читаемыми названиями и регионом.

Workflow откликов:

```text
POST /api/v1/orders/:orderId/bids
GET  /api/v1/contractor/bids
POST /api/v1/contractor/bids/:bidId/withdraw
GET  /api/v1/customer/orders/:orderId/bids
POST /api/v1/customer/orders/:orderId/bids/:bidId/select
```

Первый отклик автоматически добавляет аккаунту capability `contractor`. Один исполнитель может иметь только один активный отклик на заказ. Выбор выполняется транзакционно: выбранный отклик становится `selected`, остальные — `rejected`, а заказ переходит в `in_progress`. При отмене опубликованного заказа его активные отклики получают статус `cancelled`.

Приватная переписка: GET/POST `/api/v1/bids/:bidId/messages`, только заказчик и автор отклика. Новые и перенесённые сообщения вместе, limit/offset, canSend для закрытых диалогов. POST принимает text и UUID clientMessageId для безопасного повтора. Новое сообщение атомарно создаёт уведомление собеседнику; email без текста переписки, с учётом настройки messageReceived. Подробности и ограничения: [docs/bid-messaging.md](docs/bid-messaging.md).

Завершение и репутация:

```text
POST /api/v1/orders/:orderId/complete
POST /api/v1/orders/:orderId/reviews
GET  /api/v1/contractors/:contractorId
GET  /api/v1/contractors/:contractorId/reviews?limit=20&offset=0
```

Завершить заказ может только его заказчик или выбранный исполнитель. Операция идемпотентна. Автор отзыва определяется по Bearer-сессии, а получатель — как второй участник сделки, поэтому подменить его в запросе нельзя. До завершения заказа отзыв не принимается; от одного участника по одному заказу возможен только один отзыв. В публичной карточке нет email и других контактных данных.

Отзывы выдаются одной лентой вместе с перенесёнными: старый положительный отзыв получает 5, отрицательный — 2. У старого отзыва без сделки `orderId` и `orderTitle` равны `null`; фиктивные заказы не создаются. `ratingAverage` — среднее всех опубликованных оценок профиля, округлённое до двух знаков, `reviewCount` — их количество. Эти же данные используются в сортировке и `minRating`. Скрытые/оспариваемые отзывы исключены, без отзывов среднее равно `null`. Старые накопительные баллы за активность, PRO и портфолио не учитываются. Исходные знаки сохранены только для происхождения; единое SQL-представление отдаёт оценку 1–5.

Профиль исполнителя:

```text
GET /api/v1/contractor/profile
PUT /api/v1/contractor/profile
GET /api/v1/contractors/:contractorId
```

`PUT` принимает полное состояние профиля: `displayName`, `bio`, `avatarAttachmentId`, массивы `specializationIds` и `serviceLocationIds`, а также до 20 элементов портфолио. Каждый элемент портфолио содержит название, описание и от одного до десяти `attachmentIds`. Первое сохранение профиля автоматически добавляет аккаунту capability `contractor`; повторное сохранение тех же данных идемпотентно. Публичный endpoint объединяет эти данные с рейтингом и статистикой завершённых заказов.

Загрузка файлов профиля:

```text
POST /api/v1/attachments/upload-requests
POST /api/v1/attachments/:attachmentId/confirm
GET  /api/v1/attachments/:attachmentId/download-url
GET  /api/v1/attachments/:attachmentId/preview-url
```

Backend сначала регистрирует ожидаемый файл и возвращает короткоживущий подписанный `PUT` URL. Браузер загружает файл напрямую в S3 с заголовками из `uploadHeaders`, после чего вызывает `confirm`. Подтверждение выполняет `HEAD`, сверяет MIME и размер и возвращает статус `processing`. Этот же идемпотентный endpoint можно опрашивать до `ready` или `rejected`. Профиль принимает только `ready`-вложения нужного назначения, принадлежащие текущему аккаунту. Публичные endpoints выдают временные подписанные URL только для файла, уже привязанного к публичному профилю; сырой объект и внутренние ключи через API не раскрываются. PDF всегда отдаётся с `Content-Disposition: attachment`.

Гостевые файлы заказа:

```text
POST /api/v1/guest-attachments/upload-requests
POST /api/v1/guest-attachments/:attachmentId/confirm
POST /api/v1/guest-orders
```

Первый endpoint не требует аккаунта и возвращает `attachment`, `claimToken`, `uploadUrl` и обязательные `uploadHeaders`. В production запрос также должен содержать `captchaToken`, полученный виджетом Cloudflare Turnstile с action `guest_attachment_upload`. Backend всегда валидирует токен через Siteverify и дополнительно сверяет `hostname` и `action`.

После загрузки файла браузер передаёт `claimToken` в endpoint подтверждения и опрашивает его до статуса `ready`, а затем передаёт токен вместе с `attachmentId` в массиве `temporaryAttachments`. Claim-токен является секретом доступа: backend хранит только его хеш, не позволяет использовать необработанный или отклонённый файл и атомарно запрещает привязать один файл к двум разным заявкам. После подтверждения email токен аннулируется, а владельцем файла становится созданный или найденный аккаунт заказчика.

Выдача upload URL ограничена по адресу клиента атомарным счётчиком PostgreSQL. Сам адрес в БД не сохраняется — ключ формируется через HMAC. При превышении лимита API отвечает `429` и заголовком `Retry-After`. Значения задаются через `GUEST_UPLOAD_RATE_LIMIT` и `GUEST_UPLOAD_RATE_LIMIT_WINDOW_SECONDS`. Если API стоит за reverse proxy, нужно точно указать число доверенных переходов в `TRUST_PROXY_HOPS`; по умолчанию forwarded-заголовки не принимаются.

Фоновый worker после периода хранения переводит просроченные непривязанные файлы в `cleanup_pending`, затем удаляет сырой файл, обработанный файл, превью и запись PostgreSQL. Такое промежуточное состояние исключает гонку между очисткой и привязкой файла к заказу; неудачное удаление будет повторено следующим проходом. Интервал, размер пачки и период хранения задаются через `ATTACHMENT_CLEANUP_INTERVAL_MS`, `ATTACHMENT_CLEANUP_BATCH_SIZE` и `GUEST_ATTACHMENT_RETENTION_SECONDS`.

Публичный `GET /api/v1/attachments/:attachmentId/download-url` также работает для вложений опубликованных заказов. До публикации он не раскрывает файл.

Для локальной разработки используется S3-совместимый RustFS:

```bash
docker compose up -d --wait postgres storage clamav
npm run storage:init
```

Настройки AWS S3, Yandex Object Storage, Selectel или другого совместимого сервиса задаются переменными `STORAGE_*` из [.env.example](./.env.example). Для AWS `STORAGE_ENDPOINT` можно не указывать, а `STORAGE_FORCE_PATH_STYLE` установить в `false`.

Проверки процесса:

```text
GET /health/live
GET /health/ready
```

### Диагностика и безопасные логи

`/health/live` проверяет только HTTP-процесс и не обращается к зависимостям. `/health/ready` возвращает `200 {"status":"ready"}` при ответе PostgreSQL и `503 {"status":"unavailable"}` при ошибке, ожидании более 2 секунд или начале завершения приложения. Для проверки выделен пул из одного соединения с ограничением ожидания подключения и запроса. Оба ответа запрещают кеширование. Эти проверки не обещают доступность SMTP, S3 и ClamAV: их сбой не должен выключать остальную биржу.

Каждый HTTP-ответ, включая ошибки и Swagger, получает серверный UUID в `X-Request-Id`. Тот же ID находится в `error.requestId` и поле `reqId` лога. Входящий `X-Request-Id` игнорируется. Лог завершения запроса содержит метод, шаблон маршрута (не реальный URL), статус и время в миллисекундах. Заголовки, IP, query string и тело запроса не записываются. Неожиданные ошибки сохраняют только тип и разрешённый технический код, без message, stack, cause и ответов внешних провайдеров. Это намеренное ограничение: ошибку ищут по ID события/запроса и техническому коду, а не по персональным данным.

Исключение для локальной разработки: `MAIL_TRANSPORT=development` по-прежнему печатает письма со ссылками и адресами в терминал. Не пересылайте такой вывод целиком и не используйте этот транспорт в production (конфигурация это запрещает). Сообщения об ошибках конфигурации содержат названия настроек и правила проверки, но не их значения.

Проверить фоновые задачи из папки `backend` можно независимо от запущенного API:

```bash
npm run diagnostics
```

Команда ничего не изменяет: подключение PostgreSQL принудительно read-only, миграции и воркеры не запускаются. JSON содержит количество ожидающих событий по типам, готовых к обработке и повторяемых заданий, возраст старейшего события, просроченные блокировки и состояние обработки/очистки файлов. Payload, адреса, токены, имена файлов и текст прежних ошибок не выводятся. Для production используйте отдельную роль PostgreSQL с правом SELECT.

Коды завершения: `0` — проблем не обнаружено, `1` — есть признаки задержки/повторных сбоев, `2` — проверить не удалось (БД недоступна, настройки или схема отсутствуют). Признаки проблем:

- `OUTBOX_REPEATED_FAILURES`: незавершённое событие имеет ошибку и не менее 5 попыток.
- `OUTBOX_STALE_LOCKS`: блокировка старше 5 минут — действующий срок аренды очереди.
- `OUTBOX_OVERDUE`: доступное задание ожидает более 15 минут без действующей блокировки. Отложенные в будущее повторы сюда не входят.
- `ATTACHMENTS_STALLED`: обработка файла длится более 15 минут либо очистка не завершена спустя 15 минут после истечения upload URL и последнего обновления.

Воркеры логируют ошибки, длительность непустых пачек и восстановление после сбоя. Зависшая пачка через 5 минут даёт `Worker batch stalled`, но параллельная пачка не запускается. Каждое неудачное событие outbox отдельно логируется с eventId, eventType, числом попыток, безопасной причиной и временем повтора; новые `last_error` в БД также не содержат сообщения провайдера. Старые значения эта доработка не переписывает. `application.workerDiagnostics()` предоставляет снимок обоих локальных воркеров для встраиваемого мониторинга, но не открыт по HTTP. Завершённая пачка не означает, что все письма отправлены: смотрите сообщения об отдельных ошибках и `retrying`.

Это диагностика, а не автоматические оповещения: внешний сбор логов, метрики и алерты пока не подключены. Проверка читает агрегаты, поэтому пустая очередь сама по себе не доказывает, что воркер запущен. Доставка писем и обработка файлов проверяются по мере выполнения заданий, без активных проб SMTP/S3/ClamAV.

В production обязательны `MAIL_TRANSPORT=smtp`, `TURNSTILE_SECRET_KEY` и ClamAV (`MALWARE_SCANNER=clamav`). `TURNSTILE_EXPECTED_HOSTNAME` по умолчанию берётся из `PUBLIC_WEB_URL`. TCP-порт ClamAV нельзя выставлять в публичную сеть: протокол `clamd` не предоставляет шифрование или аутентификацию. SMTP- и защитные настройки перечислены в [.env.example](./.env.example); сырые токены подтверждения заказа, регистрации и входа в PostgreSQL не сохраняются.

Интеграционные тесты используют отдельный PostgreSQL на `127.0.0.1:55432`. При заданном `TEST_S3_ENDPOINT` дополнительно выполняется реальная проверка подписанных `PUT`, `HEAD` и `GET`:

```bash
docker compose up -d --wait postgres storage clamav
npm run storage:init
TEST_DATABASE_URL=postgresql://naitimastera:naitimastera_test@127.0.0.1:55432/naitimastera_test \
TEST_S3_ENDPOINT=http://127.0.0.1:59000 \
npm run test:integration
docker compose down
```

Контейнер хранит данные в `tmpfs`, поэтому это только тестовая база.

Миграции для другой базы без `.env`:

```bash
DATABASE_URL=postgresql://user:password@host:5432/database npm run db:migrate
```

## Уведомления

```text
GET  /api/v1/notifications?limit=20&offset=0
POST /api/v1/notifications/:notificationId/read
```

Оба endpoint требуют Bearer-сессию. Список содержит только уведомления текущего аккаунта, `total` и `unreadCount` по всему его списку. Каждая запись содержит `id`, `kind`, `orderId`, `title`, `text`, `createdAt`, `readAt`. Отметка прочтения идемпотентна и отвечает `204`; для чужой или неизвестной записи возвращается `404`.

События `BidSubmitted`, `BidSelected`, `OrderCompleted` обрабатываются outbox-worker: новый отклик уведомляет заказчика, выбор исполнителя — победителя, завершение — обоих участников. Неактивные аккаунты исключаются. Вставка уведомления и задания `NotificationEmailRequested` выполняется атомарно. Уникальная пара события и получателя защищает кабинет от дубликатов при повторной или конкурентной обработке.

SMTP-ошибка не мешает появлению записи в кабинете: почтовое задание повторяется отдельно. После успешной отправки сохраняется `emailedAt`. Доставка email имеет семантику at-least-once: при аварии между принятием письма SMTP-сервером и сохранением отметки письмо может прийти повторно. В development письма выводятся в лог; настройки SMTP общие с регистрацией. Уведомления появляются после обработки событий worker, поэтому возможна небольшая задержка.

### Настройки email

```text
GET /api/v1/notification-preferences
PUT /api/v1/notification-preferences
```

Оба endpoint требуют Bearer-сессию и работают только с текущим аккаунтом. `PUT` заменяет три прежние настройки и принимает messageReceived для писем переписки; если новое поле не передано, сохраняет его прежнее значение:

```json
{
  "email": {
    "bidSubmitted": false,
    "bidSelected": true,
    "orderCompleted": true,
    "messageReceived": true
  }
}
```

По умолчанию все четыре типа писем включены, в том числе у существующих аккаунтов без записи настроек. Настройки применяются непосредственно перед отправкой email, включая повтор после SMTP-ошибки. При выключенном типе worker записывает `emailSkippedAt` и завершает почтовое задание; запись в кабинете и её статус прочтения сохраняются. Повторное включение не рассылает ранее пропущенные письма. Уже переданное SMTP-серверу письмо отозвать настройкой нельзя.

Эти настройки относятся только к событиям биржи. Письма регистрации, входа, смены email, удаления аккаунта и сообщения безопасности от них не зависят. При удалении аккаунта его настройки очищаются вместе с уведомлениями; удалённый аккаунт не может создать их заново.

## Очистка неиспользованных файлов аккаунтов

Миграция `021_unused_account_attachments.sql` добавляет `unreferenced_since`. Очистка аккаунтов **выключена по умолчанию**: `ACCOUNT_ATTACHMENT_CLEANUP_ENABLED=false`. Включать `true` и перезапускать API следует только после отдельного подтверждения физического удаления и проверки резервного копирования. Существующая очистка истёкших незакреплённых гостевых файлов не меняется.

При включении фоновый worker сначала отмечает впервые замеченные бесхозные файлы и только через **24 часа** может удалить их. Неиспользуемым считается файл без ссылок из аватара, любого проекта портфолио и **любого** заказа (включая draft/cancelled, независимо от активности аккаунта). Новая привязка сбрасывает отсчёт. Недавно загруженные файлы защищены также сроком upload-ticket. Обработка идёт ограниченными пакетами, блокировки `FOR UPDATE SKIP LOCKED` не мешают другим экземплярам worker.

Автоматическая очистка аккаунтов работает только с ключами, созданными новым upload API: `attachments/OWNER/ID`, переданными владельцу `guest-attachments/ID` и соответствующими `processed-attachments/ID/{image,preview}.webp`. Импортированные legacy-ключи исключены даже при отсутствии ссылок. Перед изменением статуса ссылки проверяются повторно в свежем snapshot после блокировки; сохранение профиля/заказа блокирует те же attachment rows. После `cleanup_pending` привязка невозможна. Ошибка S3 оставляет статус для повторной попытки; строка БД удаляется только после удаления всех допустимых ключей. Это физическое удаление, для восстановления нужна резервная копия хранилища.

Приватные GET `/api/v1/attachments/:id/owner-preview-url` и `/owner-download-url` требуют активную сессию владельца и ready-файл, не требуют публичной привязки. Публичные endpoints по-прежнему не раскрывают черновики. Swagger обновлён. Реальные S3/ClamAV, claims, email-публикация, PDF, приватность, retention, legacy-исключения, гонки и retry покрыты `test/integration/frontend-profile.test.ts`; используется только случайная временная схема и bucket.
