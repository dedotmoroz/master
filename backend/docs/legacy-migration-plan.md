## Источник и воспроизведение

Дамп phpMyAdmin / MySQL 5.7, в заголовке дата **17 апреля 2022 года**. Размер 11 960 649 байт, 55 таблиц, SHA-256 `10ad4ea98d2d8cbf9d39408962be9eab8ba2e24d7413018266ec8c86d7f33557`. При интерпретации Unix-поля `item_date` как UTC заказы датированы 24.07.2012–27.09.2021. Старый PHP пишет `$sys['now_offset']`: соответствие временной зоны требуется проверить отдельно, прежде чем фиксировать даты в новой БД.

Пользователь подтвердил: это самые свежие данные, сайт не работал с 2022 года. Локальный дамп принят как окончательный источник; более новая выгрузка не требуется. Файлы проверяются из локального дерева старого сайта.

## Согласованные правила переноса

- Данные переносятся как рабочие, не архивируются из-за возраста. Опубликованные заказы остаются открытыми, снятые с публикации не публикуются заново. Даты и приватность сохраняются. Неизвестные состояния требуют отдельного разбора.
- По решению пользователя исключаются заказы без владельца, без описания и со статусом удаления; отклики без исполнителя и без текста, а также все зависимости исключённых записей. Новых фиктивных владельцев и текстов не создаём.
- Оригинальный SQL и файлы не удаляются. Исключение — фильтр импорта, а не очистка источника.
- Массовые письма, уведомления о старых событиях и сессии не создаются. Исторические отзывы сохраняют исходную шкалу и происхождение.

Фильтр реализован в `scripts/legacy/import-selection.ts`, покрыт тестами и используется аудитом и импортом. После всех согласованных исключений: 63 заказа, 86 откликов, 12 вложений, 16 сообщений не переносятся. В загрузку вошли 1 019 заказов, 3 137 предложений (2 869 рабочих откликов с историей версий), 465 сообщений. Для файлов остаётся 433 ссылки заказов; доступность файлов определяется отдельной антивирусной проверкой. Причины пересекаются, их нельзя складывать как независимые потери.

Из `backend`:

```bash
npm run legacy:audit
# Другой снимок и корень файлов старого сайта:
npm run legacy:audit -- /absolute/path/dump.sql /absolute/path/legacy-site
```

Команда читает SQL как данные, не выполняет его и не подключается к БД/сети. Проверяет метаданные локальных файлов; содержимое файлов и внешние URL не открывает. В отчёте только агрегаты, без email, имён, текстов, паролей, токенов и файловых путей из записей. Это ограниченный читатель формата INSERT VALUES phpMyAdmin, а не универсальный MySQL-парсер. Неподдерживаемые INSERT и повреждённые значения останавливают чтение. Тесты используют только синтетические данные.

## Заказы: проблемы и правила

- `item_state=0`: 690; `1`: 355; `-1`: 37. В PHP `projects.default.inc.php` публичная выдача выбирает `0`; `projects.edit.inc.php` публикует через `0`, снимает через `1`. В `plugins/uinfo/inc/uinfo.profile.info.inc.php` найдено присвоение `-1` при удалении пользователя. Пользователь подтвердил исключение оставшихся 3 таких заказов после фильтра владельцев.
- У 46 заказов нет пользователя-владельца: 7 имеют ID 0, ещё 39 — ненулевой отсутствующий ID. По решению пользователя исключить из переноса вместе с зависимыми записями. Не присваивать чужому аккаунту и не создавать фиктивного владельца. Оригиналы остаются в исходном дампе.
- 16 описаний пустые; 2 заголовка длиннее 160 символов. Не подставлять выдуманный текст и не обрезать оригинал без сохранения исходного значения.
- В 546 заказах бюджет 0 или отсутствует. Рекомендуем считать это «не указан» (`NULL`), а не бесплатной работой; положительную сумму переводить в копейки точным десятичным преобразованием, не через двоичный float.
- У 808 заказов есть соответствие города из старого `sed_city`; у оставшихся 274 есть соответствие региона `sed_region`. Во всех 1 082 случаях доступен хотя бы один ключ. Повторная проверка кода уточнила первоначальный аудит: `ActiveRussianLocationSelectionPolicy` уже разрешает активные регионы, а SQL публичной выдачи учитывает `kind='region'`. Поэтому регион сохраняется как регион, без выдуманного населённого пункта и без изменения ядра географии. Числа здесь относятся к полному снимку до исключений.
- `sed_city`/`sed_region` и `sed_locations`/`sed_regions` — разные пространства ID. В заказах `item_city` не совпал ни с одним ключом `locations` из подготовленного сопоставления. Нельзя выбирать справочник только по числу ID. Дополнительно проверить согласованность страны, региона и города.
- В старом дампе выбранный исполнитель есть только у одного заказа. Нет достоверного признака завершения всех остальных работ. Не создавать `completedAt` и завершённые сделки на основании возраста заказа или снятия с публикации.

**Решение пользователя:** предложение архивировать заказы по возрасту отклонено. Сохраняем исходную публичность и рабочий характер данных; массовое присвоение `cancelled` или `completed` не допускается. `-1` исключается.

## Отклики и переписка

- 3 176 предложений без выбора, 1 `performer`, 46 `refuse`. Последние соответствуют отказу заказчика, а не отзыву предложения исполнителем. `performer` потенциально соответствует selected, но жизненный цикл старого заказа требует отдельного решения.
- Все ссылаются на существующие заказы. 11 ссылаются на отсутствующих исполнителей; 2 — на заказы без владельца. Это пересекающиеся категории, суммировать их как независимые потери нельзя.
- 166 пар «заказ–исполнитель» имеют повторы: 448 строк, то есть 282 сверх одной на пару. Новая модель разрешает только один submitted/selected. Нельзя просто импортировать всё как submitted или удалить повторы. Рекомендуется архив всех версий и один выбранный по явному правилу рабочий отклик (selected имеет приоритет, иначе хронология); правило утверждается до импорта.
- **3 196 приватных откликов**, 27 публичных. Приватность `item_hidden=1` обязательно сохранить; не публиковать старые сообщения в общем каталоге.
- 3 пустых текста. У 3 222 записей единица срока — часы, у 1 — дни (`functions.custom.php`, `$sed_timetype`). При этом положительных сроков в часовых записях нет: чаще это неуказанные нулевые границы, а не обещание выполнить за 0 дней. Нули → NULL; положительные часы/месяцы в другом снимке требуют явной политики перевода.
- `sed_projects_posts` имеет `post_pid` и `post_oid`. После исключений сохранены 465 сообщений, 462 достоверно связаны с откликами и доступны только собеседникам в общей ленте с новыми сообщениями. Три без связи не выдаются по API. Переписка не превращается в публичные отклики/отзывы.

## Отзывы и репутация — необходимое расширение

Все 17 старых отзывов имеют `item_pid=0`: это отзывы о пользователе, не о подтверждённой сделке. 15 оценок `-1`, 2 оценки `+1`; авторы и адресаты существуют. Одна пара повторяется дважды. Код `reviews.add.inc.php` позволяет создавать отзыв без проекта.

Обычные `reviews` требуют orderId и участников завершённого заказа. Поэтому исходные старые отзывы сохранены в `legacy_profile_reviews` без выдуманных заказов. Пользователь явно утвердил общую ленту и преобразование: **+1 → 5, -1 → 2**. Миграция 019 добавляет вычисляемый рейтинг и единое представление `reputation_reviews`; его используют все публичные отзывы, средние оценки, счётчики, фильтры и сортировка. Исходные знаки и авторы/тексты/даты сохраняются. `user_rating` и начисления `sed_rating` полностью игнорируются. Раздельного блока старых отзывов больше нет; у отзыва без сделки orderId и orderTitle равны null. Новые отзывы по-прежнему требуют завершённого заказа, а их оценки добавляются в тот же средний рейтинг.

- Все 445 ссылок `sed_attachs.att_file` ведут к существующим локальным файлам и существующим заказам. Наличие файла **не** подтверждает его безопасность или допустимый тип/размер.
- В 3 записях портфолио 2 непустые ссылки: 1 файл существует, 1 отсутствует; ещё 1 работа без изображения. Ядро требует хотя бы одно вложение на работу — пустые/потерянные сохранить как исключения, не создавать невалидное портфолио.

Нужны лимиты числа файлов, проверка связей с владельцем/заказом, хеши и отчёт о фактически загруженных объектах.

## Как строить импорт

1. **Сохранность:** до пересоздания нынешних tmpfs-контейнеров выгрузить текущую БД и файлы. Поднять отдельную целевую среду с постоянными томами; проверить восстановление. Старый сайт остаётся read-only источником для репетиции.
2. **Staging:** зафиксировать SHA-256 и снимок файлов. Отдельные run ID, версия импортера, контрольные количества и закрытая таблица исключений. Источник не исполняется как SQL в новой БД.
3. **Происхождение:** постоянные уникальные соответствия `(source, table, legacy_id) -> target_id`, checksum исходной записи, статус импорта. UUID должны быть стабильны между прогонами. ID-таблица позволяет сверять связи, повторять загрузку и строить редиректы старых URL без потери SEO.
4. **Dry-run:** сначала план записей без записи в рабочие таблицы; итог по каждой сущности: ready / archive / quarantine / requires-decision. Пропуски и их пересечения считаются явно. Архив с ПД — с ограниченным доступом и согласованным сроком хранения, не публичный JSON.
5. **Загрузка:** справочники → аккаунты без сессий → профили/архив → заказы → отклики/назначение в транзакции → отдельные исторические отзывы → файлы и их ссылки. Никаких искусственных согласий пользователя и подтверждённых гостевых submission.
6. **Побочные эффекты:** не вызывать обычные пользовательские команды так, чтобы массово отправились welcome-письма, уведомления об откликах или назначении. Во время импорта бизнес-воркеры целевой среды остановлены; техническая проверка файлов запускается контролируемо. Не импортировать старые задания в новый outbox.
7. **Приёмка:** сверить количества по статусам и причинам, FK, UUID-карты, суммы в копейках, приватность, отсутствие дублей после повтора, оригиналы текстов/дат и файлы по хешам. Проверить отсутствие исходящих писем и новых сессий. Без явной политики не перезаписывать изменённые пользователем записи при повторном прогоне.
8. **Переключение:** репетиция на свежей копии, короткая остановка записи на старом сайте, финальный согласованный дамп БД и файлов, повторяемый импорт и проверки. Во многих таблицах нет надёжного updated_at: простого инкремента по ID недостаточно для изменений и удалений. Старую систему не удалять; откат после новых записей на новой требует отдельного плана согласования, а не только переключения DNS.

## Что не переносится в рабочие таблицы автоматически

Пароли/сессии/токены; права старых администраторов; SMTP/секреты/конфигурация PHP; логи/IP/онлайн/кеши; старые платные рейтинговые начисления и PRO-права. Форум, блоги, страницы, личные сообщения и финансы требуют решения о read-only архиве или отдельной миграции, не молчаливого удаления. Источник сохраняется как защищённый снимок.

## Решения до записи данных

1. Исторические отзывы включены в общую выдачу и рейтинг с оценками 5/2. Перенесённая переписка подключена к приватным GET/POST `/api/v1/bids/:bidId/messages`: 462 сообщения доступны собеседникам, три без надёжной связи с откликом остаются закрытыми.
2. Повторы откликов сохраняются в `legacy_bid_versions`: рабочим становится выбранный, иначе последний по дате и ID. Пользователю не приписываются вымышленные отказы/отзывы старых версий.
3. Внешние аватары не скачиваются автоматически. Форум, статьи и единственная финансовая строка остаются в исходном снимке до отдельной задачи.

Повторный запуск завершённого импорта того же снимка — no-op, не перезаписывает изменённые аккаунты/профили. Другой снимок в непустую БД автоматически не загружается.
