# Переписка по откликам

## HTTP

Оба метода требуют Bearer-сессию. Только заказчик заказа и автор **конкретного** отклика получают доступ. Публичность отклика, наличие другого отклика на тот же заказ или роль admin не дают доступ к чужой переписке. Чужой и несуществующий UUID возвращают одинаковый 404 BID_NOT_FOUND; некорректный UUID — 400. При неактивном аккаунте любого участника переписка недоступна.

```text
GET  /api/v1/bids/:bidId/messages?limit=20&offset=0
POST /api/v1/bids/:bidId/messages
```

GET возвращает `items`, `total`, `limit`, `offset`, `canSend`. В items: id, bidId, orderId, authorId, text, createdAt. Новые и перенесённые сообщения вместе, newest first (createdAt DESC, id DESC), стабильное разрешение совпадений внутри read model. Лимит 1–100, offset 0–1 000 000. Для показа чата снизу вверх клиент разворачивает полученную страницу; переходы между страницами остаются offset. `authorId=null` возможен только у перенесённого сообщения с утраченным автором.

POST:

```json
{
  "clientMessageId": "4c056c88-c3a9-4e20-b4fd-2811aa47b5fb",
  "text": "Когда удобно обсудить работу?"
}
```

Создавайте `clientMessageId` через `crypto.randomUUID()` один раз на новое сообщение. Повтор после потери ответа отправляется с тем же UUID и текстом — вернётся тот же 201 и прежнее сообщение, без второго уведомления или списания лимита. Один UUID с другим текстом даёт 409 MESSAGE_IDEMPOTENCY_CONFLICT. Ключ действует в рамках пары отклик/автор; одинаковые ключи двух собеседников не конфликтуют. Пока оба аккаунта активны, повтор уже сохранённого сообщения работает и после закрытия диалога.

Автор и время определяются сервером. Поля authorId, orderId, recipientId, createdAt и прочие неизвестные поля тела отклоняются. Текст хранится как обычная строка, не HTML: frontend должен экранировать его, а не вставлять через innerHTML. После trim допустимо 1–5 000 символов, NUL запрещён. В первом срезе нет вложений, редактирования, удаления сообщений, WebSocket, read receipts и отдельного списка диалогов: сообщения доступны по ID отклика из кабинета заказчика/исполнителя.

## Когда можно писать

Новые сообщения разрешены при заказе published/in_progress и отклике submitted/selected. Draft, completed, cancelled или rejected/withdrawn/cancelled у отклика дают 409 CONVERSATION_READ_ONLY. История остаётся доступна участникам, `canSend=false`. После выбора другого исполнителя отклонённый отклик не позволяет продолжать переписку. Идемпотентный повтор не создаёт новых сообщений.

Лимит — 20 новых сообщений за минутное окно на аккаунт, общий для всех его откликов. Превышение — 429 и Retry-After. Счётчик атомарный в PostgreSQL. В БД хранится HMAC ключа, а не текст сообщения. Чтение сообщений не расходует этот лимит.

## Уведомления

Новое сообщение, запись message_received собеседнику и NotificationEmailRequested в outbox сохраняются одной транзакцией. Если уведомление не удалось сохранить, сообщение тоже откатывается. Себе отправитель уведомление не получает. Почта уходит через существующий worker с повторами и at-least-once доставкой.

Уведомление содержит orderId и bidId; текст сообщения не копируется ни в inbox, ни в email. Новые письма с bidId содержат ссылку `/account/messages/?bidId=BID_ID`, фронтенд открывает соответствующий диалог только после авторизации. ID в ссылке не даёт доступа без сессии участника. Старые уже отправленные письма не переписываются.

В GET/PUT `/api/v1/notification-preferences` добавлено email.messageReceived, по умолчанию true. False отключает только email, уведомления в кабинете остаются. Старый PUT без этого поля сохраняет его прежнее значение; прочие три поля по-прежнему обязательны. Предпочтение проверяется перед каждой почтовой попыткой, включая повторы. После emailSkippedAt повторное включение не рассылает старые письма.

## Перенесённая история и удаление аккаунта

В исходной миграции сохранены 465 сообщений. Из них 462 имеют надёжную связь с откликом/заказом и доступны в единой ленте. 3 сообщения без bidId остаются в закрытой таблице, но не выдаются по API. Нельзя угадывать собеседника по тексту/названию заказа. Read model также отбрасывает несовпадение заказа и автора, не входящего в пару собеседников. Перенесённая история не создаёт уведомлений задним числом.

При удалении аккаунта удаляются новые и старые сообщения связанных диалогов и message_received у обеих сторон; ожидающие почтовые задания помечаются обработанными. Другие виды уведомлений не затрагиваются этой дополнительной очисткой. Отправка/чтение использует те же account → order → bid блокировки, что выбор исполнителя и удаление, и не может восстановить переписку после очистки. Уже отправленное письмо отозвать нельзя; в нём нет тела сообщения.

Миграция `020_bid_messages.sql` добавляет таблицу новых сообщений и объединяющее SQL-представление. Старые строки не переписываются, уведомления не создаются. Swagger содержит оба метода, модель canSend, nonce, ошибки и настройки email.
