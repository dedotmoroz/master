# Исходящая почта на Raspberry Pi (Debian 13)

Это **подготовленный установщик**, не установленная служба. Он запускается вручную из обычного SSH/локального терминала с `sudo`. Ограничение NoNewPrivileges в MCP не отключается и не обходится.

## Что меняется

- Устанавливаются Postfix, OpenDKIM и инструменты проверки из Debian.
- Создаётся внутренняя Docker-сеть `naitimastera-mail`: `172.30.25.0/28`.
- SMTP слушает **только** `127.0.0.1:25` и адрес этой сети `172.30.25.1:25`; LAN/WAN не слушает.
- Передавать письма могут локальные процессы и единственный адрес бэкенда `172.30.25.2`. Не подключайте к этой сети другие контейнеры и не выдавайте этот IP другим приложениям.
- Разрешён envelope sender `no-reply@naitimastera.ru` и пустой отправитель для служебных возвратов. Подпись DKIM применяется к `From: no-reply@naitimastera.ru`.
- SMTP внутри приватной сети не использует пароль или TLS. Исходящая доставка получателям требует STARTTLS. Это **не** публичный SMTP для почтовых клиентов.
- При недоступности подписывающего фильтра письма временно отклоняются, а не отправляются без подписи.
- Очередь и ключи хранятся на диске хоста; сервисы запускаются после Docker. Максимальный размер письма — 1 МиБ, срок в очереди — сутки, лимит приёма — 20 сообщений в минуту с одного клиента. При менее 1 ГиБ свободного места приём останавливается. Это предохранители, не строгая дисковая квота или защита от компрометации приложения.
- При установке **внешняя доставка отключена** через `defer_transports=smtp`. Никаких тестовых писем или рассылки старым пользователям нет.

Установщик не меняет Nginx, роутер, DNS, VPN, SSH, настройки самого Docker и действующее окружение приложения. Не перезапускает приложения. Если другая почта/сеть уже существует, прекращает работу вместо перезаписи. Не копируйте параметры домашней сети в `mynetworks`.

## 1. Проверить и запустить

Нужны все файлы этой папки рядом со скриптом. Если папка скопирована в `/home/pi/naitimastera-mail-setup`, выполните **на Raspberry**, не на Mac:

```sh
cd /home/pi/naitimastera-mail-setup
less install-mail.sh
sudo bash install-mail.sh --install
sudo bash install-mail.sh --check
```

Скрипт откажется работать без root, на неподдерживаемой ОС или внутри контейнера. Пакеты устанавливаются с временным запретом автостарта, чтобы SMTP не открылся до настройки ограничений. Чужой `policy-rc.d` не заменяется. Перед изменениями создаётся закрытая резервная копия в `/var/lib/naitimastera-mail/backup.*`.

Повторный успешный запуск не меняет ключи и не перезапускает почту. После неудачной установки повторный запуск требует ручного разбора: автоматически удалять пакеты, ключи или очередь он не будет.

## 2. DNS: записи в панели управления доменом

Перед изменениями сохраните текущую DNS-зону. Это значения для **нынешнего** внешнего IP `77.37.150.17`; при смене IP их нужно пересмотреть.

| Тип | Имя | Значение |
| --- | --- | --- |
| A | `mail` | `77.37.150.17` |
| TXT | `@` | `v=spf1 ip4:77.37.150.17 ~all` |
| TXT | `_dmarc` | `v=DMARC1; p=none` |
| TXT | `nm202611._domainkey` | Публичное значение, созданное **на вашей Raspberry** |

Если SPF/DMARC уже появились — объединить/согласовать существующую политику, а не создавать вторую запись. SPF не заменяет DKIM. DMARC `p=none` — наблюдение, не защита от подделки; адрес `rua` пока не добавлен, поскольку получатель отчётов не выбран.

Публичный DKIM:

```sh
sudo cat /etc/opendkim/keys/naitimastera.ru/nm202611.txt
```

В DNS обычно нужно вставить TXT-значение из кавычек, соединив части, без внешних скобок и комментария. **Файл `nm202611.private` никому не передавайте и не добавляйте в Git.**

У провайдера можно запросить PTR `77.37.150.17 → mail.naitimastera.ru`. Нынешняя согласованная PTR `broadband-77-37-150-17.ip.moscow.rt.ru` сама по себе не мешает тесту, но получатели могут ограничивать доставку с broadband-адресов. Установщик PTR не меняет и не обещает доставляемость.

**Не добавляйте MX на этот сервер:** текущая установка не принимает внешнюю почту. Для поддержки, DMARC-отчётов и возвратов нужен отдельно выбранный реально работающий почтовый ящик/маршрут. До production-подключения нужно согласовать обработку возвратов — одной исходящей почтой этот пункт не решён.

## 3. Проверить DNS и разрешить доставку

```sh
sudo python3 dns-check.py
sudo postqueue -p
sudo bash install-mail.sh --enable-delivery
```

Команда разрешения требует совпадения A, единственного SPF с нашим IP, DKIM-ключа и DMARC; при ошибке DNS доставку не включает. Также отказывается включать её, если очередь не пуста: сначала нужно проверить, какие сообщения там находятся. Она **не очищает и не сбрасывает очередь**. Не включайте доставку до проверки конфигурации и решения вопроса с возвратами.

## 4. Подключение бэкенда — отдельный шаг

Файл `mail.compose.yml` — **дополнение**, основной `production.compose.yml` остаётся без изменений. Скопируйте его рядом с используемым compose, например `/srv/naitimastera/mail.compose.yml`, и используйте оба файла во всех последующих командах развёртывания:

```sh
cd /srv/naitimastera
sudo docker compose -f production.compose.yml -f mail.compose.yml config --quiet
# Применять только после DNS, разрешения доставки и согласования адресов тестирования:
sudo docker compose -f production.compose.yml -f mail.compose.yml up -d --no-deps backend
```

Последняя команда **пересоздаёт бэкенд**. Требуется согласовать тестовые адреса и обработку возвратов. Установщик этого автоматически не делает.

### Сохранение настройки при последующих деплоях

В репозитории deploy-скрипты теперь используют общий `deploy/compose-command.sh`, а CI загружает его вместе с `mail.compose.yml`. На сервере эти файлы должны лежать в `/srv/naitimastera` рядом с deploy-скриптами.

Локальная почта активируется для команд деплоя только наличием `/srv/naitimastera/.mail-enabled`. Без маркера внешний SMTP остаётся без изменений. Маркер создавать **после проверки сети, DNS и готовности Postfix**, при согласованном подключении бэкенда. Сам почтовый установщик не создаёт этот маркер.

При маркере и отсутствии overlay или сети деплой останавливается, а не сбрасывает SMTP-настройки. `pull`, `up` и проверка конфигурации используют оба compose-файла. Одноразовые maintenance-команды `run` (миграции/инициализация S3) намеренно используют только основную сеть с явными SMTP-параметрами: они не отправляют письма и не должны занимать статический адрес уже работающего бэкенда. Для SMTP-тестов применять `exec` в действующем бэкенде, а не `run`.

Не создавать маркер и не применять overlay вслепую: сначала проверить фактические адреса контейнеров, почтовую сеть и параметры окружения; сохранить резервную копию deployment-файлов и проверить пустоту почтовой очереди. Наличие маркера не означает, что серверное применение уже выполнено.

### Узкое подключение без расширения прав MCP

Если MCP не имеет доступа к Docker, подготовленный комплект `connect-mail.py`, четыре deployment-файла и `manifest.json` можно скопировать в `/home/pi/naitimastera-mail-connect`. После просмотра кода запускать **в собственном терминале Raspberry**:

```sh
sudo python3 /home/pi/naitimastera-mail-connect/connect-mail.py --apply
```

Manifest создаётся при подготовке комплекта: SHA-256 каждого файла и SHA-256 исходных deploy-скриптов из проверенного коммита. При несовпадении файлов скрипт останавливается. Исходные копии файлов сохраняются в закрытой папке `/srv/naitimastera/backups/mail-connect-*`.

Скрипт проверяет Postfix/DNS, пустую очередь почты и отсутствие необработанных событий приложения, SMTP-сеть и отсутствие изменений других переменных окружения. Не подтягивает новый образ приложения: локальный тег должен совпадать с образом работающего бэкенда. Затем сохраняет overlay, helper, deploy-скрипты и маркер и пересоздаёт **только backend** с `--no-deps --pull never`. После готовности проверяет SMTP из контейнера без отправки письма и неизменность остальных контейнеров. При ошибке восстанавливает прежнюю конфигурацию бэкенда; если восстановление не удалось, завершает работу с ошибкой для ручного разбора. Реальные адреса/пароли из `.env` не печатает и не меняет. Новые разрешения Docker пользователю MCP не выдаются.

SMTP_FROM=`Найти мастера <no-reply@naitimastera.ru>`, SMTP_HOST=`172.30.25.1`, порт `25`, SMTP_SECURE=`false`, без логина/пароля. Внутренний адрес Docker не должен появляться в публичном DNS.

## Контроль и резервное копирование

```sh
sudo bash /home/pi/naitimastera-mail-setup/install-mail.sh --check
sudo postqueue -p
sudo journalctl -u postfix -u postfix@- -u opendkim --since '1 hour ago'
df -h /var/spool/postfix
```

Не публикуйте полные журналы и очередь: там могут быть адреса получателей. Для мониторинга отслеживать остановку служб, сообщения старше 5 минут, рост очереди и свободное место. Канал уведомлений ещё не выбран — автоматические оповещения пока не настроены.

Хранить зашифрованную внешнюю копию `/etc/postfix`, `/etc/opendkim.conf`, `/etc/opendkim`, `/etc/mailname`, `/etc/aliases`, systemd drop-ins. Ключи не выводить в чат. Согласованный backup очереди делается с остановкой **только почты**, без удаления spool. Ротация журналов остаётся штатной Debian/journald; строгий бюджет диска для журналов нужно согласовать отдельно, не менять глобальную политику других служб.

При аварии остановить только новые службы: `sudo systemctl stop postfix opendkim`. Резервные копии перечислить командой `sudo ls /var/lib/naitimastera-mail/`. Восстановление конкретной копии выполнять после просмотра; универсального удаления пакетов/томов/ключей в скрипте нет.
