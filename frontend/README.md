# Найти мастера — Next.js frontend

## Кабинет мастера и фотографии

`/account/profile/` — статическая приватная форма создания/редактирования профиля. В кабинете есть ссылка, кнопка «Добавить мастера» у вошедшего пользователя ведёт сюда; гость сначала регистрируется. Используются реальные GET/PUT contractor/profile. Только точный CONTRACTOR_PROFILE_NOT_FOUND означает пустую форму; сбой сети/другой 404 не подменяется пустым профилем. Авторизация и запоздалые ответы защищены тем же SessionController. Имя/бригада до 120 символов, описание до 5000, до 50 специализаций и мест работы, до 20 проектов с 1–10 файлами. Полный PUT сохраняет все выбранные ID и существующие вложения; поиск не сбрасывает старые значения. При сбое поля остаются в форме. Параллельное редактирование из нескольких вкладок не имеет optimistic locking: последнее сохранение заменяет профиль целиком.

Категории и регионы загружаются из справочников. Можно добавить весь регион или найти населённый пункт; свободный текст не отправляется вместо ID. Неизвестные названия сохранённых ID показываются явно и не удаляются автоматически. Предпросмотр показывает черновик текста и проверенные новые фотографии локально; публичная версия открывается отдельной ссылкой после сохранения. Автор/счётчики/рейтинг не передаются в PUT.

Загрузка: POST attachments/upload-requests → PUT выбранного File прямо в S3 со строго выданным Content-Type → POST attachments/UUID/confirm с ожиданием ready/rejected. Bearer и cookies не уходят в S3. Аватар — JPEG/PNG/WebP до 5 MiB; портфолио — те же форматы и PDF до 20 MiB. Сохранение блокируется во время передачи/проверки; в профиль попадает только ready-ID. Повтор передачи использует тот же файл/URL, повтор проверки — тот же attachmentId; после таймаута проверки есть кнопка повтора. Можно отказаться от незавершённой загрузки и выбрать другой файл. Автоматический cleanup сейчас касается только гостевых вложений. Неиспользованные файлы аккаунта остаются в хранилище: отдельная очистка для них ещё не реализована. Исходные S3-объекты не удаляются кнопками «Убрать»: эти кнопки меняют только ссылки профиля после сохранения.

Черновик, File, upload ticket и локальные blob-URL живут только в памяти страницы. Уход/смена аккаунта отменяет запросы и освобождает blob-URL; перезагрузка теряет несохранённые изменения и загрузку. Публичные аватар/портфолио получают краткоживущие preview/download URL только для готовых опубликованных вложений. Показываются безопасные обработанные изображения, PDF открывается отдельной ссылкой. Превью запрашиваются лениво при приближении к видимой области. Публичные тексты — React-текст, без HTML-инъекций. В production обязательны HTTPS и доступный браузеру адрес S3.

Для браузерного PUT и anonymous-превью требуется CORS бакета. Из backend: `npm run storage:cors -- http://127.0.0.1:4178` (для отдельного QA можно добавить `http://127.0.0.1:4180`). Скрипт читает существующие правила, сохраняет чужие и обновляет только своё: точные origins, GET/HEAD/PUT, Content-Type; без wildcard, без изменения bucket policy/ACL. Для production явно передайте HTTPS-origin сайта. Настройка локального RustFS выполнена для 4178/4180. Браузер не может обращаться к внутреннему Docker hostname — STORAGE_ENDPOINT должен быть достижим с его устройства.

Preview/Nginx разрешают только собственный GET/PUT contractor/profile, POST attachments/upload-requests, POST attachments/UUID/confirm и публичные GET preview-url/download-url. Cookies не пересылаются, Bearer только на приватные маршруты. JSON профиля ограничен 512 KiB (максимальное портфолио может не поместиться в 64 KiB), остальной JSON — 64 KiB. Бинарные файлы не проходят через Next/preview; статический экспорт сохранён.

Интеграционный тест полного цикла: из backend `TEST_DATABASE_URL=... TEST_S3_ENDPOINT=http://127.0.0.1:59000 TEST_CLAMAV_PORT=53310 node --test test/integration/frontend-profile.test.ts`. Создаёт отдельную схему и отдельный временный бакет, проверяет CORS preflight, прямую передачу, ClamAV/Sharp, запрет непроверенных/чужих файлов, сохранение/повторное редактирование без потерь, публикацию WebP и отклонение поддельного PNG. В отсутствие TEST_DATABASE_URL/TEST_S3_ENDPOINT тест явно пропускается. Перенесённые аккаунты/файлы не используются и не изменяются.

## Завершение работы и отзывы

В личном заказе in_progress/completed отображается блок «Завершение и отзыв». У выбранного отклика мастера есть ссылка «Работа и отзыв» на `/account/deals/view/?id=UUID`. Это статическая оболочка: состояние загружается приватным GET `/orders/UUID/deal`. Он доступен только заказчику и выбранному исполнителю и возвращает только собственный отзыв, включая скрытый/оспоренный. Чужие и несуществующие сделки дают одинаковый 404. Swagger и сохранённый контракт обновлены; новых миграций нет.

Завершить заказ in_progress может любой из двух участников. Требуется явное подтверждение; завершение идемпотентно, переписка становится только для чтения. Возврат в работу здесь не реализован. После успешного или неоднозначного ответа состояние перечитывается, включая заголовок личного заказа.

После завершения каждый участник оставляет один отзыв о втором: оценка 1–5 выбирается явно (нет предвыбранной пятёрки), текст 1–5000 символов. Получателя/автора задаёт сервер, а не форма. POST отзыва не идемпотентен, но уникальность order/author запрещает дубли; при сетевом сбое выполняется GET сделки и показывается уже сохранённый отзыв. Текст формы остаётся в памяти до успешного чтения/смены страницы, не сохраняется в браузерное хранилище. Повторная форма после сохранённого, скрытого или оспоренного отзыва не показывается. Публикация, изменение и удаление — разные действия: изменение/удаление в этом интерфейсе не предусмотрены.

В профиле мастера добавлена общая лента опубликованных отзывов с limit=20/offset, номерами и переходом на любую страницу. Старые отзывы не выделяются: +1 → 5, −1 → 2; общий рейтинг считает их вместе с новыми, старые баллы активности игнорируются. Отзыв исполнителя о заказчике сохраняется, но публичный профиль заказчика пока отсутствует. Для старого отзыва без заказа не создаётся вымышленная работа. На первой странице профиля показываются актуальные рейтинг и количество выполненных заказов из API.

Preview/Nginx разрешают только GET orders/UUID/deal, POST orders/UUID/complete, POST orders/UUID/reviews (Bearer обязателен) и публичный GET contractors/UUID/reviews (без cookies/Authorization). При 401 сессия очищается, при выходе/смене аккаунта старые приватные компоненты размонтируются. Все тексты выводятся как React-текст, не HTML. Новые email-уведомления без bidId ведут на приватную страницу сделки, с bidId — в диалог; старые уже отправленные письма не переписываются.

Тест frontend-orders проверяет обе роли, запреты чужим участникам/до завершения, повторное завершение, потерю ответа отзыва и восстановление через GET, запрет дубля, закрытие чата, публичный отзыв и общий рейтинг со старым отрицательным отзывом (5 + 2 → 3.5). Браузерная проверка выполнена в отдельной временной схеме тестовой базы с вымышленной сделкой; перенесённые записи не изменялись.

Next.js 16 (App Router), React 19, TypeScript, **полный статический экспорт**. Запуск разработки: `npm ci`, затем `npm run dev`. Адрес: http://127.0.0.1:4178.

Для статической версии: `npm run build`, затем `npm start`. Сборка создаёт `out/` с HTML, CSS, JS и изображениями. `npm start` запускает только локальный файловый сервер из `scripts/serve-static.mjs`, без Next.js runtime и рендера на запрос. В production достаточно отдать `out/` через Nginx или статический хостинг; Node.js на сервере фронтенда не нужен. Каждый URL каталога/карточки соответствует папке с `index.html`. Неизвестные страницы должны отвечать 404 с `404.html` (без SPA-fallback на главную).

Оригинальные логотип, фон шапки, жёлтые кнопки и изображения переключателя скопированы в `public/assets`. Старые файлы не меняются; приложение от старой папки больше не зависит.

Главная и каталоги `/orders/`, `/masters/` генерируются при сборке как статическая оболочка. Данные, справочники категорий и регионов загружаются из публичного API в браузере. Данные БД не включаются в HTML или JS при сборке; без JavaScript доступна оболочка с состоянием загрузки. Поиск, регион, специализация, бюджет и сортировка применяются кнопками «Найти»/«Применить». Параметры и номер страницы сохраняются в URL, пагинация — limit=20/offset; есть переход на произвольную страницу. Никакой серверной фильтрации в Next.js нет: её выполняет отдельный бэкенд по запросу браузера.

Каталоги и карточки показывают настоящие публичные записи из API. Вход и регистрация по email, размещение заказа, отклики, выбор исполнителя, переписка, завершение, отзывы и кабинет мастера подключены. «Добавить мастера» ведёт на регистрацию или редактор профиля; аватар и портфолио загружаются и отображаются на сайте. Файлы новых заказов пока не подключены. Публичные тексты выводятся обычным React-текстом, без HTML-инъекций. При недоступности API показывается ошибка с повтором, без демо-подмены.

Проверки: `npm run check`, `npm test`, `npm run build`, затем `npm run test:export`.

Карточки — фиксированные статические страницы `/orders/view/?id=UUID` и `/masters/view/?id=UUID`. Поэтому новые заказы и мастера открываются без пересборки `out/`. Их содержимое загружается клиентом из API; 404/ошибки обрабатываются в интерфейсе. HTTP-код самой статической оболочки карточки остаётся 200, даже если API ответил 404. Старые демо-URL `/orders/1/` удалены. Индивидуальных SEO-HTML с данными заказа/мастера в таком режиме нет.

## Подключение к API

По умолчанию браузер обращается к `/api/v1` на том же origin. `npm start` передаёт публичные GET-запросы каталогов/справочников на `http://127.0.0.1:3000` без cookies/Authorization. Для auth разрешены только POST запроса/подтверждения регистрации и входа, GET текущего аккаунта, DELETE текущей/всех сессий. Bearer передаётся только для GET me и DELETE session(s); cookies не передаются нигде. Для auth запрещены query string, cross-site Origin, неподходящий метод/Content-Type, тело больше 4 KiB. Остальные приватные API и запись заблокированы. Страницы по-прежнему читаются только из `out/`, Next runtime не запускается. Dev-rewrites ограничены перечисленными auth/public путями; ограничения метода/тела в dev обеспечиваются самим API, production должен использовать отдельный reverse proxy.

Запустите бэкенд в отдельном терминале: `cd ../backend && npm start`. Для другого адреса локального API задайте переменную окружения `API_PROXY_TARGET` при запуске. Она не является клиентской и в bundle не включается. Файл `.env.example` — только образец; preview-сервер не читает .env автоматически.

В production отдавайте `out/` через Nginx и перенаправляйте разрешённые публичные `/api/v1/…` на бэкенд; пример — `deploy/nginx.conf.example`. Это образец HTTP-конфига для локальной проверки, не полная конфигурация публичного запуска с HTTPS. Если нужен отдельный origin API, задайте `NEXT_PUBLIC_API_BASE_URL` при сборке и настройте точный allowlist CORS на бэкенде (сейчас CORS там не включён). Сервер Next.js, ISR и Server Actions не используются. Не помещайте секреты в `NEXT_PUBLIC_*`.

## Авторизация

- `/auth/login/`, `/auth/register/` — запрос одноразовой ссылки, нейтральный ответ без раскрытия наличия email, блокировка повторной отправки и обработка 429/Retry-After.
- `/auth/login/confirm/`, `/auth/register/confirm/` — читают token из письма, сразу удаляют его из адресной строки. Подтверждение только по явному нажатию, не при открытии/префетче. После обновления страницы без token нужно запросить новое письмо. Токен подтверждения не сохраняется.
- `/account/` — текущий email/права, личные заказы и отклики. Редактирование профиля остаётся следующим этапом.

`PUBLIC_WEB_URL` бэкенда должен указывать на origin фронтенда, локально `http://127.0.0.1:4178`; после изменения перезапустите backend. В development SMTP не отправляет настоящие письма: ссылка появляется в локальном журнале бэкенда. Не публикуйте журнал — ссылка даёт доступ к аккаунту. Для публичного запуска нужен SMTP и HTTPS.

Bearer-сессия хранится в `sessionStorage` только в текущей вкладке, без localStorage, cookies и токенов в URL. При загрузке выполняется GET me; 401 очищает локальную сессию, сетевой сбой позволяет повторить проверку. Новый email-tab получает собственную сессию; другие открытые вкладки не входят автоматически. Закрытие вкладки обычно убирает локальную копию, но само по себе не отзывает сессию на сервере (браузер также может восстановить sessionStorage при восстановлении вкладки). На общем компьютере обязательно используйте «Выйти». При сетевой ошибке выхода показывается ошибка и сессия остаётся для повторного отзыва; успешный выход отзывает серверную сессию и очищает локальную копию.

Static export не может самостоятельно установить HttpOnly cookie. sessionStorage доступен JavaScript: XSS на origin может прочитать токен; это не равно защищённой HttpOnly-сессии. Не подключайте сторонние скрипты/аналитику к auth-страницам, не используйте raw HTML, настройте CSP и HTTPS перед публичным запуском. На всех страницах задан no-referrer, в Nginx-примере для `/auth/` отключён access log: одноразовая ссылка иначе попадает в логи прокси до выполнения JS. Dev-сервер Next.js может логировать URL — его журналы не предназначены для публикации.

Интеграционный тест реального API и PostgreSQL: из `backend` выполнить `TEST_DATABASE_URL=... node --test test/integration/frontend-auth.test.ts`. Тест создаёт и удаляет только случайную схему внутри указанной тестовой базы, не отправляет письма и не затрагивает перенесённые аккаунты.

## Размещение и личные заказы

- `/orders/new/` — настоящая форма размещения. Справочники категорий/регионов и поиск населённых пунктов берутся из API; выбирается ID из результатов, а не свободный текст. Бюджет необязательный, перевод в копейки выполняется без округления float.
- Создание использует существующий `POST /guest-orders` и для гостя, и для вошедшего пользователя. Все новые заказы требуют подтверждения email; у вошедшего пользователя email предварительно заполнен, но может быть изменён. В этом случае подтверждение переключит вкладку на аккаунт указанного email. Прямого API создания опубликованного заказа для вошедшего пользователя сейчас нет.
- До подтверждения показывается «Проверьте почту», заказ ещё не опубликован. `/orders/confirm/` очищает token из URL, публикует только по явной кнопке и устанавливает сессию через проверку GET me. Если вход не сохранился после публикации, заказ доступен через обычный вход по email. Повторное подтверждение одного submission не дублирует заказ. Сам POST размещения не идемпотентен: после сетевого сбоя сначала проверяйте почту, не отправляйте форму многократно.
- `/account/orders/` и `/account/orders/view/?id=UUID` — статические приватные оболочки, данные запрашиваются только после проверки сессии. Пагинация limit/offset; чужие записи возвращают 404. 401 очищает локальную сессию. При выходе/смене аккаунта личные компоненты размонтируются, запоздалые ответы предыдущей сессии не отображаются.
- Редактирование/отмена доступны только draft/published. Полный PUT сохраняет существующие attachmentIds; файлы не теряются при изменении текста/бюджета. Отмена требует отдельного подтверждения и сохраняет запись со статусом cancelled. При конфликте статуса 409 карточка перечитывается. Публикация старого черновика отдельной кнопкой пока не реализована (такого метода в текущем API нет).
- Фото и PDF подключены: до 10 файлов по 20 МБ, проверка ClamAV и очистка изображений перед привязкой. Согласие включает публикацию текста, фото и документов; юридические документы для публичного запуска не разрабатывались.

Preview-прокси дополнительно разрешает только POST guest-orders(/confirm), GET customer/orders, GET/PUT customer/orders/UUID и POST /cancel. Cookies нигде не пересылаются; Bearer передаётся только на приватные пути. Тела ограничены 64 KiB, запрещены cross-site Origin, приватные query-токены и посторонние методы. В Nginx-примере добавлены соответствующие маршруты и отключены access logs для ссылки `/orders/confirm/`. В production необходимо отдельно настроить HTTPS, лимиты запросов/антиспам и юридические тексты.

Проверка гостевого и личного сценария на настоящем API: из `backend` выполнить `TEST_DATABASE_URL=... node --test test/integration/frontend-orders.test.ts`. Все записи тестовые, в случайной временной схеме; проверяются отсутствие публичного заказа до email, публикация, повторное подтверждение, редактирование/отмена, чужие аккаунты и запреты после выбора исполнителя.

## Настройки аккаунта и безопасность

`/account/settings/` — статическая приватная оболочка, ссылка из кабинета. Смена email запрашивает POST `/auth/email-change-requests` с Bearer и `{email}`; текущий адрес не меняется до подтверждения. Письмо отправляется на новый адрес, после подтверждения сервер уведомляет прежний email и отзывает **все** сеансы аккаунта. Вход после смены выполняется по новому адресу. Учитываются занятый/неизменившийся email, 401 и Retry-After; повторные запросы защищены от двойного нажатия и имеют паузу.

Запрос удаления — POST `/auth/account-deletion-requests` с Bearer и `{}` после отметки о последствиях. Это только запрос письма, не удаление. При заказах `in_progress` в роли заказчика или выбранного исполнителя сервер возвращает конфликт; проверка повторяется при подтверждении. После удаления профиль/личные данные очищаются, сеансы отзываются, файлы удаляются фоновым обработчиком; история завершённых сделок и отзывов сохраняется. Эта существующая процедура удаления аккаунта отдельна от выключенной автоматической очистки неиспользованных файлов.

Ссылки писем ведут на `/auth/email-change/confirm/` и `/auth/account-deletion/confirm/`. Они работают без входа, но **ничего не выполняют при открытии**. Токен удаляется из URL и hash до нажатия, хранится только в памяти страницы и отправляется исключительно в JSON-теле публичного POST `/auth/...-requests/confirm`, без cookies и Bearer. Дублированные/неправильные токены отклоняются. Финальное удаление требует отдельной отметки о необратимости; кнопка выключена, пока отметка не поставлена. Сторонние скрипты на эти страницы не добавлялись; Nginx отключает access log для `/auth/`, на страницах задан no-referrer. Не обновляйте страницу во время подтверждения: токен в storage не сохраняется.

Успех отображается только после 204. После успешного подтверждения (и при неизвестном сетевом результате) текущая сессия перепроверяется через `me`: отозванная сессия удаляется, другой открытый действующий аккаунт **не** разлогинивается вслепую. Письмо определяет целевой аккаунт, а не открытый сеанс — это явно указано перед подтверждением. При потере ответа действие могло успеть выполниться: повторная одноразовая ссылка может вернуть ошибку и не считается доказательством, что первое действие не прошло.

Выход со всех устройств в кабинете и настройках защищён диалогом с отменой. Только отдельная кнопка подтверждения вызывает существующий DELETE `/auth/sessions`; простой выход из вкладки остаётся без дополнительного диалога. Ошибка отзыва сеансов не скрывается и не объявляется успешным выходом.

Preview proxy, Next development и Nginx разрешают только узкие методы: POST обоих запросов с сессией и POST обоих `/confirm` без неё. Тела до 4 KiB, query-токены запрещены preview-прокси, cookies не пересылаются, ответы no-store. Изменения API/Swagger и миграции не требовались. Проверки: обычные frontend test/check/build/test:export и backend `TEST_DATABASE_URL=... node --test test/integration/frontend-account-settings.test.ts`. Интеграция использует только синтетические аккаунты в случайной временной схеме; проверяет смену адреса, отзыв ссылок/сеансов, сохранение другого сеанса, повторную проверку незавершённых работ, удаление и сохранение завершённой сделки. Браузерная QA не меняет и не удаляет реальные аккаунты.

## Центр уведомлений

`/account/notifications/` — статическая оболочка личной ленты, `/account/notifications/settings/` — настройки четырёх типов email. В верхней панели после входа есть колокольчик со счётчиком. Эти страницы доступны из кабинета, имеют `noindex` и не содержат личных данных в HTML export.

Счётчик запрашивает `GET /notifications?limit=1&offset=0` раз в 30 секунд только в видимой вкладке, при возврате к ней/фокусе и после отметки прочтения. Нет запросов без подтверждённой сессии и пересекающихся фоновых запросов одного счётчика; принудительное обновление отменяет устаревший запрос. Сбой показывается как недоступный счётчик, а не «0». Контекст меняется при смене аккаунта без перемонтирования страниц подтверждения email; старые ответы отменяются и не переносят счётчик между аккаунтами.

Лента использует `limit=20&offset=…`, номера страниц и прямой переход, без курсоров. Первая страница обновляется раз в 30 секунд в видимой вкладке, остальные — вручную. Новые события могут сдвигать offset старых страниц. При сетевом сбое загруженная страница сохраняется с предупреждением; после выхода/смены аккаунта личный экран размонтируется. Тексты выводятся React-текстом, без HTML-инъекций.

«Отметить прочитанным» отправляет идемпотентный POST `/notifications/UUID/read` без тела и ждёт 204; после подтверждения перечитываются лента и счётчик. Простое открытие ссылки **не** отмечает уведомление прочитанным. Автоматической отметки всех и удаления уведомлений нет. Новый отклик ведёт к личному заказу, выбор исполнителя/завершение — к сделке, сообщение — в конкретный диалог по `bidId`. Отсутствующие записи обрабатываются целевой страницей; при отсутствии старого bidId ссылка на переписку не выдумывается.

Email-переключатели загружают серверные настройки и сохраняют все четыре булевых значения через PUT `/notification-preferences`: отклики, выбор исполнителя, сообщения, завершение. Настройки не меняют уведомления в кабинете и обязательные письма входа/безопасности; повторное включение не рассылает ранее пропущенные письма. При потере ответа можно повторить сохранение того же набора. Несохранённые изменения живут только в памяти страницы.

Preview proxy, Next development и Nginx разрешают только GET notifications, POST notifications/UUID/read и GET/PUT notification-preferences. Bearer только в заголовке, cookies не пересылаются, ответы не кэшируются; в preview запрещены чужой Origin, лишние query и тела PUT больше 64 KiB. API и Swagger уже содержали эти методы и не изменялись.

Проверки: `npm test`, `npm run check`, `npm run build`, `npm run test:export`; из backend — `TEST_DATABASE_URL=... node --test test/integration/frontend-notifications.test.ts`. Интеграция использует случайную временную схему: чужая лента/прочтение, 401, offset, повторное прочтение, четыре настройки, подавление email без потери ленты и отсутствие повторной рассылки пропущенных писем. Браузерная проверка выполнена на синтетическом аккаунте в отдельной схеме, без изменения импортированных данных.

## Загрузка вложений заказов

`/orders/new/` загружает файлы как гостевые даже у вошедшего пользователя: заказ принадлежит адресу из формы после подтверждения email. Claim-токены живут только в памяти компонента, не попадают в URL, storage, поля DOM или Bearer. До публикации публичные ссылки на файлы возвращают 404. После подтверждения файлы принадлежат заказчику. Перезагрузка теряет незавершённую форму и гостевые claims; не перезагружайте страницу во время проверки/отправки.

Сначала запрашивается подписанный PUT, затем файл отправляется напрямую в S3 без cookies и Bearer, подтверждается и ожидает проверки. При сетевой ошибке сохраняется попытка: повтор не создаёт новый файл, если ticket уже получен. Пока попытка не завершена, отправка/сохранение заблокированы; можно отказаться от файла. Готовые изображения показываются локально, PDF — по имени. На сервере MIME/размер и содержимое проверяются заново; изображения очищаются и получают WebP-превью.

В кабинете можно добавить и убрать вложения при редактировании draft/published. Отмена редактирования не изменяет заказ. Приватные GET `/attachments/UUID/owner-preview-url` и `/owner-download-url` доступны только владельцу, в том числе для черновиков/отменённых заказов. Публичные карточки показывают галерею и ссылки PDF; неизвестные/недоступные файлы и просроченные ссылки имеют повтор загрузки.

В production задайте публичный `NEXT_PUBLIC_TURNSTILE_SITE_KEY` перед `npm run build` в паре с backend `TURNSTILE_SECRET_KEY` и hostname. Защита гостевых загрузок не отключается клиентом. Виджет загружается только в форме гостевой загрузки; каждый новый upload-request требует отдельной проверки. Для CSP разрешите `https://challenges.cloudflare.com` в script-src/frame-src согласно [Cloudflare](https://developers.cloudflare.com/turnstile/reference/content-security-policy/). Локальный режим без Turnstile сохраняет серверный rate limit. Настройте CORS bucket для точного origin фронтенда (`npm run storage:cors` в backend), никогда не добавляйте туда API Bearer.

Preview/Next development/Nginx разрешают узкие гостевые POST ticket/confirm и приватные GET owner URLs. Для production кроме приведённых location нужны HTTPS и лимиты запросов на reverse proxy. Имена файлов и тексты выводятся обычным React-текстом.

## Отклики и выбор исполнителя

- В публичной карточке заказа добавлена форма для вошедшего пользователя: текст до 5000 символов, необязательные цена и срок. Рубли преобразуются в копейки без float-округления, срок — целые дни 1–100000. По умолчанию отклик приватный; публичность выбирается явно. Публичный список откликов пока не выводится — видимость сохраняется в API.
- Бэкенд запрещает отклик на свой заказ, второй активный отклик и отклики на неопубликованный заказ. Отдельный профиль для отправки не требуется; первый отклик добавляет право contractor. Если профиль мастера ещё не создан, ссылка на него покажет отсутствие публичного профиля.
- `/account/bids/` показывает свои отклики, полные тексты, цены и статусы с limit=20/offset и переходом на любую страницу. Активный отклик можно отозвать после подтверждения. Снятая с публикации карточка заказа может быть недоступна, сам отклик остаётся в кабинете.
- В личной карточке заказа есть приватный список откликов, переход в профиль мастера и выбор исполнителя с отдельным подтверждением. После выбора заказ in_progress, выбранный отклик selected, остальные submitted — rejected. Состояние заказа и список перечитываются; действия при устаревших данных обрабатываются как конфликты. Смена исполнителя в интерфейсе не предусмотрена.
- Все операции выполняются через SessionController.authorized: 401 убирает сессию, смена аккаунта/выход защищают от запоздалых ответов. Повторные клики блокируются. После сетевой ошибки отправки нужно проверить «Мои отклики» перед повтором; POST отправки не идемпотентен.
- Preview и Nginx дополнительно разрешают только POST orders/UUID/bids, GET customer/orders/UUID/bids, POST customer/orders/UUID/bids/UUID/select, GET contractor/bids и POST contractor/bids/UUID/withdraw. Методы сообщений описаны ниже. Сохраняются ограничения Origin, Bearer, query-параметров и размера тела.

Интеграционный тест frontend-orders теперь также проверяет отправку/отзыв/повторный отклик, запрет дублей и self-bid, приватность чужого списка, выбор, повторный выбор, статусы конкурирующих откликов и запреты после выбора. Он использует настоящий API и изолированную схему PostgreSQL.

## Переписка

- `/account/messages/?bidId=UUID` — фиксированная статическая оболочка. Переход «Переписка» есть у каждого отклика в кабинете обеих сторон, в том числе у закрытых откликов. Данные загружаются только после авторизации. Чужой диалог возвращает одинаковый 404; 401 очищает сессию. Выход или смена аккаунта размонтирует личный экран и не позволяет запоздалому ответу показать историю другого аккаунта.
- `GET /bids/UUID/messages?limit=20&offset=…` объединяет новую и безопасно связанную старую историю. API сортирует от новых к старым, интерфейс разворачивает одну страницу в хронологическом порядке. Есть номера страниц и прямой переход, без курсоров. При появлении новых сообщений offset старых страниц может сдвигаться; история обновляется вручную, первая страница — автоматически каждые 10 секунд в видимой вкладке и при возврате к ней. Пересекающихся фоновых запросов нет, уход со страницы отменяет чтение.
- `canSend=false` оставляет историю и убирает отправку новых сообщений. При недоступности диалога история очищается. При сетевом сбое обновления уже загруженная история сохраняется с предупреждением. Тексты выводятся React-текстом, без HTML-инъекций; неизвестный автор старого сообщения обозначен явно.
- На новое сообщение создаётся `crypto.randomUUID()`. При потере ответа та же попытка повторяется с неизменными UUID и текстом — сервер возвращает уже сохранённое сообщение. Пока ответ неизвестен, текст зафиксирован; двойные нажатия блокируются. Уже сохранённая попытка может быть подтверждена повтором даже после закрытия диалога. При 429 учитывается Retry-After и показывается обратный отсчёт. После успешной отправки открывается первая страница и перечитывается история.
- Текст и nonce живут только в памяти страницы: не сохраняются в URL, localStorage/sessionStorage или логах. Перезагрузка/закрытие страницы теряет черновик и незавершённую попытку — до подтверждения отправки не перезагружайте страницу. Если всё же перезагрузили после сбоя, сначала проверьте историю перед новым сообщением. Сохранение черновиков, read receipts, WebSocket, вложения, удаление/редактирование и отдельный общий список диалогов не реализованы.
- Новые email-уведомления с bidId ведут прямо в статический диалог. Письмо не содержит текст сообщения; без входа оно не раскрывает историю. Старые отправленные письма с прежними URL не меняются. В development настоящая почта по-прежнему не отправляется.
- Preview/Nginx разрешают только GET/POST `/api/v1/bids/UUID/messages`; Bearer обязателен, cookies не пересылаются, запросы cross-site блокируются preview-прокси, тело до 64 KiB. Query разрешён только для GET и только limit/offset. Прочие операции над сообщениями закрыты. Для отдельной изолированной проверки preview можно запустить с `PREVIEW_PORT=4180 API_PROXY_TARGET=http://127.0.0.1:3001 npm start`; по умолчанию порт остаётся 4178.

Проверки: `npm test`, `npm run check`, `npm run build`, `npm run test:export`. Из backend: `npm test`, `npm run typecheck` и `TEST_DATABASE_URL=... node --test test/integration/frontend-orders.test.ts test/integration/bid-messages.test.ts test/integration/frontend-auth.test.ts`. Проверяются реальная фиксация сообщения с потерей ответа, отсутствие дубля/повторного уведомления, ответы обоих участников, приватность, закрытие конкурирующего диалога и идемпотентный повтор после закрытия.
